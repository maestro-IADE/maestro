# 커밋과 PR 규칙

여러 에이전트가 각자 브랜치에서 일하고 Lead가 합치는 흐름을 기준으로 해요.

## 브랜치

- 워커는 자기 워크트리 브랜치에서만 커밋한다. 다른 브랜치로 체크아웃하거나 기준 브랜치에 직접 커밋하지 않는다
- 합치기와 push, PR은 앱이 사용자 승인을 받아 한다(`maestro merge-request`). 에이전트는 직접 하지 않는다
- 기준 브랜치를 받아 올 때는 자기 워크트리에서 기준 브랜치를 merge한다(PR 모드가 아니면 rebase도 된다)

## 하지 않는 것

- 강제 푸시. 푸시가 거절되면 멈추고 보고한다
- 공유 작업 폴더(프로젝트 폴더)에서 `git stash`
- 넓게 지우는 명령: `git reset --hard`, `git clean -f`, `git checkout -- .`, `git restore .`, `git branch -D`
- `--no-verify`로 훅 건너뛰기. 훅이 실패하면 원인을 고친다
- 요청받지 않은 `git commit --amend`. 푸시된 커밋은 amend·rebase·reset으로 다시 쓰지 않는다
- `git config` 바꾸기(사용자 이름, 메일, 서명, 훅 경로 포함)

## 커밋

- 한 커밋에 한 가지 변경. 관련 없는 정리는 섞지 않는다
- 제목은 무엇을 바꿨는지 현재형으로 50자 안팎(72자 넘지 않게). 본문에는 왜 바꿨는지. 저장소에 자기 규칙(예: Conventional Commits)이 있으면 그것을 따른다
- 커밋하기 전에 스테이징된 파일을 확인한다(`git diff --cached --stat`). 의도하지 않은 파일이 섞였으면 뺀다
- 커밋하지 않는 것: 자동 생성 파일, 로컬 설정, 비밀 값, 계획·메모·임시 파일, 의도하지 않은 lockfile 변경. 저장소가 추적하는 생성물(예: 마이그레이션 메타)은 원본과 같이 커밋한다
- 커밋이 실패하면 실패라고 보고한다. "변경 없음"이나 성공으로 쓰지 않는다

## PR

- 제목: 바뀐 것 한 줄
- 본문: 왜 / 무엇을 / 어떻게 확인했나(돌리지 않은 검사는 돌리지 않았다고) / 남은 위험. 저장소 PR 템플릿이 있으면 그것을 따른다
- 리뷰 지적은 고치거나, 고치지 않는 이유를 답한다

## 합치기 전 점검

- 기준 브랜치 최신을 받아 충돌을 먼저 푼다. 충돌은 양쪽 의도를 모두 살리고, 한쪽을 통째로 고르는 것은 분명할 때만 한다
- 최신 기준을 받은 상태에서 테스트와 빌드가 통과하는지 확인한다
- 다른 워커와 같은 파일을 건드렸는지 확인하고, 겹치면 순서를 정해 하나씩 합친다
