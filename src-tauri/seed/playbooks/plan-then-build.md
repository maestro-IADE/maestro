# 계획 먼저, 구현은 나중

바로 고치지 않고, 먼저 조사와 계획을 세워 사용자 승인을 받은 뒤 구현하는 절차예요. 기본 지휘(`default.md`)의 공통 규칙을 함께 따라요.

## 구성

| 역할 | 페르소나 | 인원 | 맡는 일 |
|---|---|---|---|
| 조사 | 없음 | 1 (선택) | 코드를 고치지 않고 조사만 |
| 계획 | `~/.maestro/personas/architect.md` | 1 (작으면 Lead가 직접) | 구조와 순서, 선택지 비교 |
| 기획 | `~/.maestro/personas/planner.md` | 1 (선택) | 목표·범위·완료 기준 |

## 언제

- 요청이 모호하거나 범위가 클 때
- 기존 구조를 바꾸는 일(아키텍처, 데이터 형식)
- 사용자가 "어떻게 할지 먼저 보여 줘"라고 할 때

## 절차

1. **조사.** 관련 코드를 읽는다. 크면 조사만 하는 워커를 둔다
   ```
   maestro worktree create --name survey --prompt "코드를 고치지 말고 조사만: <질문>. 관련 파일과 현재 동작을 파일:줄과 함께 정리해 줘"
   ```
2. **묻기.** 조사로 답이 안 나오고 계획을 바꿀 만한 것만 묻는다. 질문마다 추천 답을 붙여 한 번에 묻는다. 되돌리기 비싼 것(데이터 형식, 공개 API, 비용, 법적 문제)은 추천 답을 기본값으로 삼아 넘어가지 않고 답을 기다린다. 고를 것이 정해진 질문은 캔버스에 묻는다(`maestro ask`, 보기에 추천을 적는다). 질문이 둘 이상이면 묶음으로 한 번에 묻는다(`maestro ask --file questions.json`): 사용자가 하나씩 답하고 모두 한 번에 보내서, 답이 메모 하나로 온다. 답을 계획에 반영한 뒤 질문을 치운다(기본 지휘의 "캔버스에 그리고 묻기")
3. **계획.** 아키텍트·기획자 관점으로 정리한다
   - 목표 한 줄과 하지 않을 것
   - 바꿀 파일과 순서. 지우거나 바꿔 끼우는 것은 그렇다고 적는다
   - 선택지가 있으면 비교와 추천, 버린 안과 이유
   - 완료 기준: 어떤 명령을 돌려 무엇이 보이면 끝인지
   결정할 가치가 있으면 PRD의 결정 기록 형식으로 남긴다
4. **승인.** 사용자에게 계획을 보이고 턴을 끝낸다. 승인 전에는 구현하지 않는다. 답이 없으면 기다린다
5. **구현.** 승인된 계획대로 "나눠서 구현"이나 "구현 → 리뷰 반복" 플레이북으로 넘긴다. 워커 명세에 계획의 해당 부분과 완료 기준을 그대로 넣는다
6. **대조.** 끝나면 계획과 실제를 비교한다. 계획에서 달라진 점, 하지 않은 항목, 완료 기준별 결과(`evidence-gate.md`의 세 칸)를 보고한다
