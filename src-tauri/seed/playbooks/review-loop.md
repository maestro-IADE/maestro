# 구현 → 리뷰 반복

구현 워커가 만든 것을 리뷰어가 읽고 지적하면, 구현 워커가 고치는 것을 꼭 고칠 지적이 없어질 때까지 반복하는 절차예요. 리뷰는 라운드마다 새 리뷰어가 해요. 기본 지휘(`default.md`)의 공통 규칙을 함께 따라요.

## 구성

| 역할 | 페르소나 | 인원 | 맡는 일 |
|---|---|---|---|
| 구현 | `~/.maestro/personas/implementer.md` | 1 | 명세대로 구현하고 지적을 고침 |
| 리뷰 | `~/.maestro/personas/reviewer.md` (위험이 큰 변경은 `skeptic.md`) | 라운드마다 1 (새로) | 고치지 않고 지적만 |

## 언제

- 실수하면 비싼 변경(보안, 데이터, 공개 API)
- 사람이 리뷰하기 전에 한 번 걸러 두고 싶을 때

## 절차

1. 구현 워커를 만들고 구현 담당 페르소나를 잇는다
   ```
   maestro worktree create --name impl --prompt "<명세>"
   maestro ref add --to impl --path ~/.maestro/personas/implementer.md
   ```
2. 구현이 끝나면(`## 보고`의 `상태: 완료`, 커밋 있음) 리뷰어를 **새로** 만든다. 리뷰어에게는 브랜치, 비교 기준, 명세의 요구사항만 준다. 구현 워커의 설명이나 대화는 넘기지 않는다
   ```
   maestro worktree create --name review-1 --prompt "impl 브랜치를 <기준 브랜치>와 비교해 리뷰해 줘. 코드는 고치지 말고 지적만. 요구사항: <명세의 요구사항>. 바뀐 줄을 중심으로 보되 바뀐 함수를 부르는 곳도 확인. 지적마다 파일:줄, 문제, 왜 문제인지, 고칠 방향, 등급(꼭/권장/취향)"
   maestro ref add --to review-1 --path ~/.maestro/personas/reviewer.md
   ```
3. 리뷰 결과에서 **꼭 고칠 것**만 골라 구현 워커에게 보낸다. 꼭 고칠 것: 잘못된 동작, 보안, 데이터 손실, 명세 위반, 바뀐 로직에 테스트 없음. 나머지(권장·취향·범위 밖)는 후속 작업으로 모은다
   ```
   maestro send --to impl --text "리뷰 지적 중 이것만 고쳐 줘: 1) 파일:줄 … 2) …"
   ```
4. 고친 뒤 다음 라운드는 새 리뷰어(`review-2`)가 본다. 앞 라운드 지적 목록을 주고 "고쳐졌는지와 새 문제"를 보게 한다. 최대 3라운드
5. 끝나면 `evidence-gate.md`를 거쳐 합치고, 사용자에게 고친 지적·남은 지적(고치지 않기로 한 것과 이유)을 함께 보고한다

## 멈출 때

- 3라운드를 돌아도 꼭 고칠 지적이 남으면 멈추고 사용자에게 판단을 묻는다
- 같은 지적이 두 라운드 연속 나오면 구현 워커가 지적을 잘못 이해했거나 지적이 틀렸을 수 있다. 다시 보내지 말고 사용자에게 올린다

## 하지 않는 것

- 리뷰어 지적을 다 넘기지 않는다. 고르는 기준은 위 3번이다
- 같은 리뷰어에게 고친 결과를 다시 보게 하지 않는다. 앞 판단에 끌려간다
- 이유 없는 지적("이게 더 낫다")은 꼭 고칠 것으로 치지 않는다
