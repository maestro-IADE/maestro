# 근본 원인 디버깅

증상을 덮지 않고 원인을 찾아 고치는 절차예요. 재현부터 고정하고, 가설을 증거로 가린 뒤, 실패하는 테스트를 먼저 두고 가장 작게 고쳐요. 기본 지휘(`default.md`)의 공통 규칙을 함께 따라요.

## 구성

| 역할 | 페르소나 | 인원 | 맡는 일 |
|---|---|---|---|
| 추적 | `~/.maestro/personas/debugger.md` | 1 | 재현을 고정하고 원인 쪽으로 좁힘. 고치지 않음 |
| 가설 확인 | `~/.maestro/personas/debugger.md` | 0–3 (가설이 여러 영역에 걸칠 때) | 고치지 않고 가설 하나를 확인하거나 기각 |
| 고치기 | `~/.maestro/personas/implementer.md` | 1 | 확정된 원인만, 실패하는 테스트 먼저 |

## 언제

- 오류나 잘못된 동작의 원인을 모를 때
- 한 번 고쳤는데 다시 나타났을 때
- 원인 후보가 여러 영역(화면, 서버, 설정, 환경)에 걸칠 때

## 절차

1. **증상 적기.** 재현 순서, 기대한 결과, 실제 결과, 오류 메시지 원문, 언제부터인지를 적는다
2. **재현 고정.** 추적 워커가 한 번에 돌릴 수 있는 재현 명령(테스트, 스크립트, 요청)을 만든다. 재현이 안 되면 가설로 넘어가지 않는다. 로그·환경 차이를 더 모으거나 사용자에게 재현 정보를 묻는다
   ```
   maestro worktree create --name trace --prompt "고치지 말고 추적만: <증상>. 1) 실패하는 재현 명령 만들기 2) 최근 변경(git log, 필요하면 git bisect)과 호출 경로를 거슬러 원인 후보 좁히기. 결과는 재현 명령, 출력, 후보와 근거"
   maestro ref add --to trace --path ~/.maestro/personas/debugger.md
   ```
3. **가설 카드.** 후보마다 한 장씩 적는다: 원인, 맞다면 보일 것, 틀리다면 보일 것, 그걸 가르는 확인 명령. 후보가 한 영역이면 추적 워커가 이어서, 여러 영역이면 가설마다 확인 워커를 둔다(고치지 않게)
4. **원인 확정.** 확인 결과로 가설을 `확인`/`기각`/`모름`으로 나눈다. 확인된 원인이 증상을 다 설명하는지 본다. 다 기각되면 새 가설로 3번부터. 근거 없이 "아마 이것"으로 넘어가지 않는다
5. **실패하는 테스트 먼저.** 고치기 워커가 원인을 겨누는 테스트를 먼저 쓰고, 고치기 **전** 코드에서 그 테스트가 실제로 실패하는 것을 보인다. 처음부터 통과하면 원인을 겨누지 못한 테스트다
6. **가장 작게 고치기.** 원인만 고친다. 원인과 상관없는 정리는 하지 않고 후속 작업으로 적는다. 테스트가 통과하고, 전체 테스트도 그대로인지 본다
7. **되돌려 확인(권장).** 고친 부분만 잠시 되돌리면 테스트가 다시 실패하는지 본다. 테스트가 정말 이 수정을 지키는지 확인하는 것이다
8. **합치기와 기록.** `evidence-gate.md`를 거쳐 합친다. 원인·재현·수정·테스트를 문서 → RAG → 문제 해결 기록 형식으로 남긴다

## 멈출 때

- 고쳤는데 같은 증상이 남는 일이 3번이면 멈춘다. 원인을 잘못 짚었거나 구조 문제일 수 있으니, 지금까지의 가설·결과를 정리해 사용자와 방향을 정한다
- 재현이 사용자 환경에서만 되면 필요한 정보(버전, 설정, 로그)를 구체적으로 묻고 기다린다

## 하지 않는 것

- 증상만 가리는 수정(오류 삼키기, 시간 늘리기, 재시도 추가, 특수 처리 분기)을 원인 수정이라고 하지 않는다. 임시로 꼭 필요하면 그렇다고 적고 사용자에게 알린다
- 확인 단계에서 여러 워커가 동시에 고치지 않는다. 고치는 건 한 명만
- 한 번에 여러 가지를 바꿔 보지 않는다. 바꿀 때마다 하나씩 확인한다
- 실패하는 테스트를 지우거나 건너뛰게 해서 통과시키지 않는다
