# 증거로 완료 판정

워커가 "끝났다"고 해도 그대로 믿지 않고, 지금 브랜치에서 새로 돌린 결과로만 완료를 정하는 절차예요. 혼자 쓰기보다 다른 런북의 **합치기 직전**에 끼워 써요. 기본 지휘(`default.md`)의 공통 규칙을 함께 따라요.

## 구성

| 역할 | 페르소나 | 인원 | 맡는 일 |
|---|---|---|---|
| 판정 | Lead 자신 | - | 기준 정하기, 명령 돌리기(작은 변경), 최종 판정 |
| 검증 | `~/.maestro/personas/verifier.md` | 0–1 (큰 변경이나 Lead가 돌리기 어려운 검사) | 고치지 않고 명령만 새로 돌려 기준별 결과표 |
| 반증 | `~/.maestro/personas/skeptic.md` | 0–1 (보안·데이터·공개 API) | 주장과 증거만 받아 깨뜨려 보기 |

## 언제

- `[maestro] 워커 … 완료` 메모를 받고 그 브랜치를 합치려 할 때
- 사용자에게 "고쳤어요", "통과해요", "다 됐어요"라고 말하기 직전

## 절차

1. **기준 적기.** 원래 요청과 명세를 다시 읽고, 끝났다고 말할 조건을 번호로 적는다. 조건마다 "무엇을 하면 무엇이 보인다"는 확인 방법을 붙인다. 명령은 저장소의 CI 설정·`package.json`·`Cargo.toml` 등에서 찾는다. 확인 방법이 없는 조건은 "수동 확인 필요"로 표시해 둔다
2. **대상 고정.** 워커 브랜치의 HEAD 커밋을 적는다(`git -C <워크트리> rev-parse --short HEAD`). `## 보고`의 `커밋`과 다르면 워커에게 먼저 묻는다. 커밋되지 않은 변경이 있으면 커밋하게 한다
3. **새로 돌리기.** 그 HEAD에서 명령을 처음부터 다시 돌린다. 워커 보고에 적힌 결과는 다시 쓰지 않는다
   - 작은 변경: Lead가 워커 워크트리에서 직접 돌린다(고치지는 않는다)
   - 큰 변경, 오래 걸리는 검사: 검증 워커를 만든다
   ```
   maestro worktree create --name verify-<작업> --prompt "고치지 말고 검증만. <작업> 브랜치(<커밋>)에서 아래를 새로 돌려 기준마다 명령, 종료 코드, 통과·실패·건너뜀 수, 출력 일부를 표로. 1) … 2) …"
   maestro ref add --to verify-<작업> --path ~/.maestro/personas/verifier.md
   ```
4. **기준별 판정.** 조건마다 `통과` / `실패` / `확인 불가` 중 하나. 통과는 명령 출력이나 `파일:줄` 인용이 있을 때만이다
   - 통과로 치지 않는 것: 테스트 0개 실행, 건너뜀, 출력 없이 종료 코드만, 도구의 "성공" 응답, 범위 일부만 돈 검사, 이전 커밋에서 돌린 결과
   - 출력이 `tail`·`head`로 잘렸으면 요약 줄(통과·실패 수)이 보일 때까지 다시 본다
   - 버그 수정이면 재현 테스트가 수정 **전** 코드에서 실패했다는 증거가 있어야 한다(워커 보고에 없으면 수정을 되돌린 상태나 기준 브랜치에서 돌려 확인한다)
5. **반증(선택).** 보안·데이터·공개 API 변경이면 반증 워커에게 주장과 diff만 넘긴다. 구현자의 설명이나 대화는 넘기지 않는다
6. **고치고 다시.** `실패`가 있으면 실패한 조건과 출력만 구현 워커에게 보낸다. 고친 뒤 새 HEAD에서 3번부터 다시 한다. 이 반복은 3번까지
   ```
   maestro send --to <작업> --text "검증 실패: 조건 2 (명령 …, 종료 1, 출력 …). 코드를 고쳐 줘. 테스트·검사·기준을 약하게 바꾸지 말 것"
   ```
7. **합치기.** 모든 조건이 `통과`이거나, `확인 불가`가 남았으면 사용자에게 알리고 그래도 합칠지 물은 뒤 병합을 요청한다. `--verified`에는 Lead가 직접 확인한 것만 쓴다
   ```
   maestro merge-request --to <작업> --verified "<커밋>에서 직접 확인: cargo test 통과 42·실패 0, npm run build 종료 0. 확인 못 함: 좁은 창 화면(볼 수 없음)"
   ```
8. **합친 뒤.** 프로젝트 폴더에서 빌드·테스트를 다시 돌린다. 여러 브랜치를 합쳤으면 마지막 상태에서 한 번 더 돌린다. 합치기 전 결과는 합친 뒤의 증거가 아니다

## 판정 보고

사용자에게는 세 칸으로 나눠 말한다.

- **확인함**: Lead나 검증 워커가 이번에 돌린 명령과 결과
- **워커 주장**: 보고에만 있고 다시 확인하지 않은 것
- **확인 못 함**: 무엇을, 왜 못 했는지

## 멈출 때

- 끝났다고 말할 조건을 적을 수 없으면 사용자에게 기준을 묻는다
- 돌릴 명령이나 실행 환경이 없으면 "확인 못 함"으로 보고하고 멈춘다. 결과를 짐작해 채우지 않는다
- 6번 반복이 3번을 넘거나, 같은 조건이 같은 이유로 두 번 실패하면 멈추고 사용자에게 판단을 묻는다
- 판정 중에 워커 브랜치가 움직였으면 이전 판정은 버리고 2번부터 다시 한다

## 하지 않는 것

- 테스트를 지우거나 건너뛰게 하거나, 기준·임계값을 낮춰 통과시키지 않는다. `--no-verify`로 훅을 넘기지 않는다
- 실패를 재실행으로 덮지 않는다. 가끔만 실패하는 테스트는 그 테스트만 따로 여러 번, 그리고 기준 브랜치에서도 돌려 이번 변경 탓인지 가린다
- 한 검사의 통과로 다른 검사를 대신하지 않는다. 린트가 깨끗해도 빌드는 따로 돌리고, 테스트가 초록이어도 요구사항은 조건별로 따로 맞춰 본다
- 검증 워커는 코드를 고치지 않는다
