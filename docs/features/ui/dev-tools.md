# 개발용 시험

## 요약

개발 빌드(`npm run tauri dev`)의 위 막대에 있는 "dev 모드" 표시를 누르면 개발용 시험 목록이 나와요. 시험은 에이전트도 AI도 쓰지 않고 앱의 한 부분을 직접 돌려 봐요. 지금은 넷이에요. **캔버스 CLI 시험**, **채팅 창구 시험**(에이전트가 그린 것이 채팅에 먼저 보이고, 올리거나 버리는 것. 아래 "채팅 창구 시험"), **깊은 영역 시험**(여러 겹으로 겹친 영역에 들어가고 나오기), **OS 알림 시험**(가짜 에이전트들의 일을 앱의 알림 규칙에 넣어 진짜 OS 알림으로 보내는 것. 아래 "OS 알림 시험"). 먼저 캔버스 CLI 시험이에요. 빈 시험 캔버스를 띄우고, 캔버스에 그리는 `maestro` 명령(관계 선언, 그리기, 질문, 읽기, 지우기)을 진짜 CLI 실행 파일로 차례대로 실행해요. 명령마다 답과 통과 여부가 보이고, 캔버스에 그려지는 것을 눈으로 확인해요. "종료"를 누르면 시험 화면이 닫히고 시험이 남긴 것은 지워져요.

## 동작

**들어가기**: 위 막대의 "dev 모드"(경고색 글자, 개발 빌드에만 있어요) → 메뉴의 "캔버스 CLI 시험", "채팅 창구 시험", "깊은 영역 시험", "OS 알림 시험"(`Bell`). 앞의 셋은 지금 보고 있는 프로젝트에서 실행돼요. 프로젝트가 열려 있지 않으면 "시험할 프로젝트를 먼저 열어 주세요" 알림이 떠요. OS 알림 시험은 프로젝트가 없어도 열려요(아래). 메인 창과 떼어 낸 창 모두 같아요.

**시험 화면**: 위 막대 아래를 다 덮어요. 왼쪽(420px)이 단계 목록, 오른쪽이 시험 캔버스예요.

- 머리: "캔버스 CLI 시험", 오른쪽에 "종료". 아래에 실행하는 CLI 경로(`~/.maestro/bin/maestro`, 에이전트가 쓰는 그 파일).
- 버튼: "끝까지 실행"(남은 명령을 차례로), "한 단계"(다음 명령 하나), "처음부터"(캔버스를 비우고 다시), 실행 중에는 "멈춤"(지금 명령까지만 하고 멈춤). 오른쪽에 "N개 중 M개 통과".
- 단계마다: 번호(실행 중 스피너, 통과 ✓, 실패 !), 이름, 터미널에 치는 그대로의 명령, `--file`이 있으면 "파일 내용 보기", 캔버스나 답에서 볼 것 한 줄, 실행 뒤에는 "답 · 종료 코드 · 걸린 시간"(누르면 출력, 실패하면 펼쳐져 있어요).
- "거절돼야 통과"라고 적힌 단계는 CLI가 오류로 끝나야 통과예요(검사가 일하는지 보는 단계).
- 명령 사이에는 1.5초쯤 기다려요. 캔버스가 그림을 받고 0.5초 뒤 저장하는데, `erase`와 `canvas`는 그 저장된 파일을 읽어서예요.
- 맨 아래 "에이전트에게 갈 메모": 시험이 남긴 질문 블록에 답하면, 에이전트가 받았을 `[maestro] 질문 … 답했어요` 메모가 여기에 보여요(보내지는 않아요).
- 시험 캔버스는 보통 캔버스와 같아요(블록을 끌고, 영역을 접고, 우클릭 메뉴를 써요). 아래쪽 에이전트 입력창만 없어요.

**단계** (정확한 목록과 순서는 `src/devSteps.ts`의 `STEPS`예요. 아래는 묶음이에요)

| 묶음 | 명령 | 볼 것 |
|---|---|---|
| 준비 | `maestro --help`, `relation define --name 시험-의존 …` | 명령 목록, 관계 패널에 '시험-의존' |
| 그리기 | `draw --file 1-흐름.json`, `draw --file 2-고치기.json`, `canvas --brief true` | 영역 셋(설계 → 구현 → 검증)이 flow로 놓이고 테두리 색이 다름. 있는 블록의 내용이 고쳐지고 영역 안에 영역이 더해짐. 읽은 답에 영역·블록·화살표·lint |
| 단계와 상태 | `draw --file 4-단계와-상태.json`, `step --area "배포 순서"`, `step … --to 3`, `state --area 서버 --to 장애`, `canvas` | 단계 영역의 머리에 ◀ 1 / 3 ▶, 넘길 때마다 보이는 블록이 바뀜. 상태 영역은 상태에 따라 블록과 선이 바뀜. 읽은 답에 `mode`, `current`, `in_steps` / `in_states` |
| 묶음 | `draw --file 9-묶음.json`, `canvas --brief true` | '배포 점검표' 묶음에 블록 셋이 세로 한 줄로. 읽은 답에 `stack: true`와 순서 있는 `holds` |
| 질문 | `ask` 세 가지(하나 고르기, 여러 개 + 기타, 주관식), `ask --file 6-질문-묶음.json`, `ask --file 7-지울-묶음.json` | 질문 블록 셋, 그리고 묶음 영역 둘(머리에 1 / 3, 화살표로 답하면 다음 질문으로) |
| 보기 블록 | `show --file 시험-그림.svg --title …`, `show --file 시험-페이지.html --title …` | 막대 그림이 든 보기 블록과 작은 페이지가 든 보기 블록(안의 버튼이 눌림). 시험이 쓰는 파일은 `~/.maestro/dev/`에 만들어지고 시험이 끝나면 지워져요 |
| 선택 | `selection` | 캔버스에서 골라 둔 블록(질문 블록도) |
| 설명과 화면 | `draw --say …`(묶음 그리기에 붙음), `say --text …`, `focus --title 구현 --say …`, `tidy` | 위쪽 가운데에 설명 한 줄이 떴다가 사라짐. 화면이 '구현'으로 가고 테두리가 밝아짐. 영역 안의 블록이 줄 맞춰지고 그린 것들이 다시 놓임 |
| 지우기 | `erase --from … --to …`, `erase --title …`, `erase --question …`(질문 하나, 그리고 묶음 이름으로 묶음째), `erase --view …`, `erase --all true`, `relation remove` | 화살표, 영역(안의 블록은 남음), 질문 블록, 질문 묶음 하나가 사라짐. 마지막에 `erase --all true`가 남은 그림, 질문 블록 둘, 질문 묶음 하나, HTML 보기 블록을 모두 지워 캔버스가 비고, 시험 관계도 사라짐(질문에 답해 보려면 그 전에 "한 단계"로 멈춰서. 답하면 메모가 오른쪽에 나옴. 묶음은 메모 하나) |
| 거절돼야 통과 | 보기가 하나뿐인 `ask`, 질문이 하나뿐인 묶음, 단계가 있는 묶음(`stack` + `steps`), 이미지도 HTML도 아닌 파일의 `show`, 없는 이름으로 가는 화살표, 없는 상태, 범위를 벗어난 단계의 블록, 없는 이름 지우기 | 오류로 끝나고 캔버스는 그대로 |

**끝내기**: "종료"를 누르면 시험 캔버스 파일, 받지 않은 그림, 시험이 선언한 관계(`시험-`으로 시작하는 이름)가 지워져요. "처음부터"도 같은 것을 지우고 빈 캔버스로 다시 시작해요.

**깊은 영역 시험** (→ [영역](../canvas/zones.md) "들어가기")

- "dev 모드" → "깊은 영역 시험". 캔버스 CLI 시험과 같은 화면이고 명령만 달라요(`DEEP_STEPS`, 4단계).
- 그리는 것: 회사 › 제품 › 앱 › 화면 › 로그인 › 로그인 흐름, 여섯 겹으로 겹친 영역(겹마다 블록 하나 이상, 화살표 둘). 맨 안 '로그인 흐름'은 Step 셋(입력·검사·결과)이에요. 그림 하나로 그려요(그림은 그 그림이 그리는 영역만 이름으로 가리킬 수 있어서). 이어서 Step 넘기기, 맨 안쪽 블록 가리키기, `maestro canvas` 읽기(겹친 in과 current).
- 손으로 볼 것(단계마다 "볼 것"에 적혀 있어요): 차례로 더블클릭해 들어가며 경로가 넷째부터 "…▾"로 접히는지(좁은 캔버스는 셋째부터), …▾ 목록으로 나가기, 경로 아래 따로 된 Step 줄, 들어갈수록 짙어지는 바탕, 접힌 영역에 들어가도 칩이 안에 보이지 않는지. 새 탭에서 열기는 시험 캔버스가 에이전트의 것이 아니라서 되지 않아요.

**채팅 창구 시험** (→ [채팅 창구](../agents/chat-visuals.md))

- 화면은 셋으로 나뉘어요: 왼쪽 단계 목록, 가운데 시험 캔버스, 오른쪽(400px) "채팅 (대역)". 오른쪽은 에이전트의 채팅에서 입력창 위에 뜨는 카드 자리 그대로예요(`ApprovalCards`): 그림 카드와 채팅 선택지가 여기에 떠요.
- **캔버스는 닫힌 채로 시작해요**(에이전트를 전체 화면 채팅으로 볼 때와 같아요). 가운데에 "캔버스가 닫혀 있어요"가 보여요. 오른쪽 위의 "캔버스 열기 / 닫기"로 바꾸고, 카드의 "캔버스에서 보기"도 캔버스를 열어요.
- **추천 그림은 눌러서로 바뀌어요**(그래야 그린 것이 기다려요). 오른쪽 위의 "추천 그림 바로 / 눌러서"로 바꿔 볼 수 있어요. 진짜 설정을 바꾸는 것이고, 시험을 끝내면 원래 값으로 돌아가요.
- 단계(`src/devSteps.ts`의 `CHAT_STEPS`, 8개)와 해 볼 것:

| 단계 | 명령 | 해 볼 것과 볼 것 |
|---|---|---|
| 그리기: 채팅에 먼저 보여요 | `draw --say … --file 1-흐름.json` | 채팅 대역에 설명 한 줄과 작은 그림(영역 둘, 블록 넷, 화살표)이 든 카드. "캔버스에 올리기"를 누르면 "올린 것 1개" 줄로 바뀜 |
| 그리기: 버려 보기 | `draw --say … --file 2-검증.json` | 다음 카드에서 "버리기". 카드가 사라지고 왼쪽 "에이전트에게 갈 메모"에 버렸다는 메모 |
| 채팅 선택지와 함께 | `ask --in chat --title … --choices "설계\|구현"` | 그림 카드 아래에 선택지 카드가 따로 뜸. 고르면 답 메모 |
| 이미 있는 것 가리키기 | `focus --title 설계 --say …` | '설계' 영역의 그림만 든 카드(새로 그리지 않음). "캔버스에서 보기"로 캔버스가 열리고 화면이 그곳으로 감 |
| 보기 블록 | `show --file 시험-그림.svg --say …` | 카드에 막대 그림이 그대로 보임(캔버스에 올리기 전에도). 캔버스가 열려 있으면 캔버스의 안내와 채팅 카드가 함께 기다림(어느 쪽을 눌러도 같음) |
| 보기 블록: HTML 페이지 | `show --file 시험-페이지.html --say …` | 카드에 페이지가 작게 줄어든 모습으로 보임(카드 안에서는 눌리지 않음. 캔버스에 올리면 블록 안에서 버튼이 눌림) |
| 설명 한 줄 | `say --text …` | 그림 없는 카드("넘기기"). "바로"로 바꾸면 기다리던 것이 모두 올라가고 카드가 사라짐 |
| 바로일 때 | `draw --say … --file 3-배포.json` | "바로" + 캔버스를 닫고 실행: "캔버스를 열면 올라가요" 카드. "캔버스에서 보기"로 열면 올라가고, ×는 채팅에서만 치움 |

- 이 시험에는 지우는 단계가 없어요. "종료"나 "처음부터"가 시험 캔버스와 대기열을 모두 지워요.
- 단계의 통과 표시는 명령이 받아들여졌는지(종료 코드)만 봐요. 카드가 맞게 뜨는지, 올리기와 버리기가 맞게 되는지는 눈으로 보고 눌러 봐야 해요.

**OS 알림 시험** (→ [OS 알림](os-notifications.md))

- "dev 모드" → "OS 알림 시험". 다른 시험과 달리 열린 프로젝트를 쓰지 않아요. 대역 팀은 늘 프로젝트 "알림 시험"에 있어서 알림 제목이 "혼자 · 알림 시험"처럼 나와요. 알림 센터에 남은 시험 알림을 진짜 에이전트의 것으로 보지 않게 하려는 거예요.
- 가짜 에이전트들(대역 팀)에게 일이 생긴 것처럼 해서, 앱이 실제로 쓰는 규칙(`osNotify.ts`)이 만든 알림을 진짜 OS 알림으로 보내요. AI도 에이전트도 쓰지 않아요. 화면 위 설명에는 세 가지가 더 있어요: 앱은 원래 창이 뒤에 있을 때만 보낸다는 것, 떴는지는 눈으로 봐야 한다는 것(앱은 OS에 넘긴 것까지만 알아요), 개발 빌드의 알림은 보낸 이가 Windows PowerShell로 보인다는 것.
- 화면은 다른 시험과 같은 꼴이에요: 왼쪽이 조작과 경우 목록, 오른쪽이 "OS에 넘긴 알림"(넘긴 시각, 제목, 본문. 새것이 위). 아직 넘긴 게 없으면 화면에 뜬 것과 비교해 보라는 한 줄이 있어요.
- 머리: "OS 알림 시험", 오른쪽에 "종료". OS 권한을 보여 주는 줄은 없어요(아래 "제약").
- "보내는 때" [바로 | 5초 뒤]: 바로는 앱이 앞에 있어도 곧바로 보내요. 5초 뒤는 보낼 것이 있는 경우마다 5초를 센 뒤(경우 옆에 남은 초), 앱처럼 Maestro 창에 포커스가 하나도 없을 때만 보내요. 그 사이 다른 창으로 가면 앱이 실제로 보내는 경우를 그대로 시험해요. 실행 중에는 바꿀 수 없어요.
- "OS 알림" [모두 | 기다릴 때만 | 끔]: 이 시험에서만 쓰는 수준이에요(툴팁 "이 시험에서만 써요 (설정은 그대로예요)"). 처음 값은 설정 → 일반 → OS 알림이고, 바꿔도 설정과 진짜 에이전트의 알림은 그대로예요. 실행 중에는 바꿀 수 없어요.
- 버튼: "끝까지 실행"(남은 경우를 차례로, 넘긴 경우 다음에는 2.5초 쉬어요), "한 단계", "처음부터"(결과와 넘긴 알림 목록을 비워요), 실행 중에는 "멈춤"(지금 보내는 것까지만). 오른쪽에 "넘김 a · 없음 b"(건너뛴 것이 있으면 "· 건너뜀 c", 막힌 것이 있으면 "· 막힘 d"이고 빨간 글자), 실행 전에는 "8단계".
- 경우마다: 번호 자리 표시(아래 표, 실행 중에는 스피너), 이름, 무엇을 하는지(알림이 없어야 하는 경우는 그 이유), 보낼 알림(제목 줄 + 본문 줄, 없으면 "(보낼 알림 없음)". 실행 전에는 지금 수준에서, 실행한 뒤에는 그때 넘긴 것). 실행 뒤에는 결과 한 줄이 붙어요. 결과는 그 경우를 실행한 수준을 기억해서, 나중에 수준을 바꿔도 결과 줄은 실행했을 때의 수준으로 말해요.

| 결과 줄 | 표시 |
|---|---|
| OS에 넘겼어요 (n개). 화면 구석이나 알림 센터에서 확인해 보세요 | ✓ |
| 보낼 알림이 없어요 (맞아요) | ✓ |
| "기다릴 때만"이라 보내지 않았어요 / "끔"이라 보내지 않았어요 | ✓ |
| 앱이 앞에 있어서 보내지 않았어요 (앱이 하는 그대로예요). 5초 안에 다른 창으로 가 보세요 | 없음(번호 그대로). 5초 뒤에서 Maestro 창에 포커스가 있었던 것으로, 보내 보지 않은 것이지 실패가 아니에요. 합계에는 "건너뜀" |
| OS가 알림을 막았어요 | !(빨간 줄). 합계에는 "막힘" |

- 경우는 8개예요(`src/devNotify.ts`의 `notifyCases`). 대역 팀은 Lead "시험 Lead"와 그 워커 "로그인 고치기"·"api 테스트", 혼자 도는 "혼자"이고, 모두 프로젝트 "알림 시험"에 있어요.

| 경우 | 하는 일 | "모두"에서 보낼 알림(제목 / 본문) |
|---|---|---|
| 승인 기다림 | "혼자"가 Bash 승인을 기다림 | 혼자 · 알림 시험 / 승인 대기 · Bash |
| 터미널 질문 | "혼자"가 터미널에서 답을 기다림 | 혼자 · 알림 시험 / 터미널 질문 |
| 병합 요청 | 워커가 병합을 부탁해 Lead가 기다림 | 시험 Lead · 알림 시험 / 병합 요청 1 |
| 채팅 선택지 | "혼자"가 채팅에 선택지를 냄 | 혼자 · 알림 시험 / 질문 · 어느 쪽으로 고칠까요? |
| 작업 끝 | "혼자"의 턴이 끝남 | 혼자 · 알림 시험 / 작업이 끝났어요 |
| 워커의 작업 끝 | 워커 "로그인 고치기"의 턴이 끝남 | 없음(Lead가 받아요) |
| 워커가 도는 동안 Lead 쉼 | 워커가 도는데 Lead의 턴이 끝남 | 없음 |
| 여럿이 한꺼번에 | 워커 둘이 승인·터미널 질문을 기다리고 "혼자"가 끝남 | Maestro / 기다림 2 · 끝남 1 |

- "기다릴 때만"이면 작업 끝은 없고, 여럿이 한꺼번에는 "Maestro / 에이전트 2개가 기다려요"예요. "끔"이면 모두 없어요.

## 구현

- 채팅 창구 시험: `DevTest.id`가 `"chat-visuals"`면 `CanvasCliTest`가 `chat`으로 그려져요. 단계는 `CHAT_STEPS`, 캔버스는 `canvasOpen`일 때만 띄우고(내리면 `gate.mount(scope, false)`가 대기열을 다시 읽어요), 오른쪽 `.dev-chat`에 `<ApprovalCards path={대역 호출자} root onCanvas />`를 그려요. `root`는 대역 호출자가 앱의 에이전트 목록에 없어서 주는 것이고(가리키는 것의 그림을 저장된 캔버스에서 읽을 때 써요), `onCanvas`는 "캔버스에서 보기"가 탭 대신 시험의 캔버스를 열게 해요. 시작할 때 `guideMode`를 기억하고 `"manual"`로 바꿨다가 끝날 때 되돌려요. 버리기의 메모는 `control::discarded`가 대역 호출자면 `maestro://dev-note`로 내보내요. `scripts/dev-steps-check.ts`가 `CHAT_STEPS`도 봐요(모두 받아들여지는 명령인지, 가리키는 이름이 첫 단계가 그린 영역인지).

- 입구: `DevBadge`(DevTools.tsx, `import.meta.env.DEV`일 때만). App.tsx와 Workspace.tsx(떼어 낸 창)의 위 막대가 그려요. 누르면 앱 공통 메뉴(`openMenu`)가 배지 아래에 떠요. 고른 시험은 `useDev`(zustand, 창마다)의 `test`에 들어가고, `WindowLayers`의 `DevScreen`이 그려요(`.dev-screen`, `position: fixed`, 위 막대 아래 전체, z-index 48: 대화상자·메뉴보다 아래).
- 시험 캔버스의 주인: 워크트리가 아니라 **대역 호출자**예요. 경로는 `<프로젝트 폴더>/__maestro_cli_test__`(디스크에 만들지 않아요, `dev::caller`). `control::locate`가 이 경로를 그 프로젝트의 가짜 워크트리(`dev::stand_in`, 이름 "CLI 시험", 에이전트·워커 없음)로 답해요. 그래서 모든 경로(route)가 에이전트가 부를 때와 똑같이 돌아요. 캔버스 파일은 `canvases/__maestro_cli_test__.json`(앱 데이터, 프로젝트 저장소 밖), 그림 대기열과 선택의 키도 이 경로예요.
- 실행: `dev_cli_run(root, args, file)`(dev.rs)가 `~/.maestro/bin/maestro(.exe)`를 `maestro_env`(에이전트 터미널과 같은 `MAESTRO_URL`, `MAESTRO_TOKEN`, `MAESTRO_WORKTREE` = 대역 호출자)로 실행하고 종료 코드·stdout·stderr·걸린 시간을 돌려줘요. `file`은 `~/.maestro/dev/cli-test.json`에 쓰고 `--file <그 경로>`를 붙여요. 그래서 CLI 실행 파일 → 로컬 서버(approval.rs, 토큰 검사) → `control::handle` → 그림 대기열 → `maestro://draw` → 캔버스까지 진짜 길을 다 거쳐요.
- 시작과 끝: `dev_cli_begin(root)`가 `clear`(캔버스 파일, 대기열, 선택, `시험-` 관계 삭제) 뒤 `{ scope, cli }`를 주고, `dev_cli_end(root)`가 `clear`만 해요. 화면은 "처음부터" 때 캔버스를 먼저 내리고 200ms 뒤에 `begin`을 불러요(내려가는 캔버스의 늦은 저장이 지운 파일을 되살리지 않게). 화면이 닫힐 때는 300ms 뒤에 `end`를 불러요.
- 캔버스: `<Canvas root scope={대역 호출자} bare />`. `bare`는 아래 에이전트 입력창(`AgentBar`, `BarButton`)을 그리지 않아요. `run` 값으로 `ReactFlowProvider`를 다시 만들어 "처음부터" 때 빈 캔버스에서 시작해요.
- 질문의 답: `control::answer_question`이 주인이 대역 호출자면 에이전트에게 보내지 않고 `maestro://dev-note`(`{ owner, note }`)를 내보내요. 시험 화면이 받아 "에이전트에게 갈 메모"에 쌓아요.
- 단계: `src/devSteps.ts`의 `STEPS`(`title`, `args`, `file`/`fileName`, `fails`, `see`, `settle`). `scripts/dev-steps-check.ts`(`npm test`)가 이 목록을 백엔드 규칙(이름 확인, 보기 수, 지울 것이 캔버스에 있는지)에 맞춰 봐요: 거절 표시(`fails`)가 붙은 단계만 거절되는지, 끝에 그린 것과 선언한 관계가 남지 않는지. 통과는 `fails`면 종료 코드 ≠ 0, 아니면 0. 실행기 `go(all)`은 `gen`(처음부터·종료 때 올라가는 번호)이 바뀌면 결과를 남기지 않고 멈추고, "멈춤"(`halt`)은 실행 중인 명령의 결과까지 적고 멈춰요.
- 시험: dev.rs `stand_in_caller_names_its_project_and_nothing_else_does`(대역 호출자 경로와 프로젝트 찾기). 화면과 실제 실행은 타입 검사와 컴파일만 했어요.
- OS 알림 시험: `DevTest.id`가 `"os-notify"`면 `DevScreen`이 `NotifyTest`(src/DevNotifyTest.tsx, 받는 것은 `onExit`뿐)를 그려요. 메뉴의 `startNotify`는 프로젝트를 확인하지 않고 `root: ""`로 열어요.
  - 경우: `src/devNotify.ts`의 `notifyCases(PROJECT, attentionItems, askText)` → `NotifyCase[]`(`title`, `see`, `before`, `after`). `PROJECT`는 DevNotifyTest.tsx의 상수 `"알림 시험"`이에요. `before`·`after`는 대역 팀(`NAMES`)의 두 모습(`NotifySnap`)이고, 경로는 `/__maestro_notify_test__` 아래라 진짜 에이전트와 겹치지 않아요. 이 파일은 순수하고 `import type`만 써요(Node가 번들러 없이 시험을 돌려요). 그래서 확인할 일 목록을 만드는 `attentionItems`(attention.ts)와 질문 글 `askText`(osNotify.ts)를 인자로 받아요.
  - 수준: 화면의 `level`(`useState`, 처음 값 `useSettings.getState().osNotify`)이에요. 설정에 쓰지 않아서 끝낼 때 되돌릴 것도 없어요. 수준 버튼과 바로·5초 뒤 버튼은 실행 중(`busy`)에 막혀요.
  - 보내기: 경우마다 `level`로 `coalesce(live(notices(before, after, level, reason), after, level))`(useOsNotify의 보내기와 같은 길)를 만들고, `deliver(out, 5초 뒤인지)`(src/ui/useOsNotify.ts)로 보내요. 결과는 `{ how, out, level }`로 남기고, 결과 줄(`said(r, c)`)은 `r.level`로 말해요. `how`(`"sent" | "none" | "focused" | "denied"`)가 표시를 정해요: `sent`·`none`은 `data-state="ok"`(✓), `denied`는 `"bad"`(!), `focused`는 표시 없음. 합계는 `how`마다 센 것(`tally`)이에요. `reason`도 useOsNotify.ts가 내보내는 것을 써요. → [OS 알림](os-notifications.md) "구현"
  - 권한은 화면에 보이지 않아요. `deliver` 안의 `permitted()`만 물어요.
  - 실행기 `go(all)`은 캔버스 CLI 시험과 같은 꼴(`gen`, `halt`)이에요. 5초 뒤면 보낼 것이 있는 경우만 1초씩 세고(`LATER_S`), 끝까지 실행은 넘긴 경우 뒤에만 쉬어요(`GAP_MS`, 2.5초). 넘긴 알림은 화면의 `log`에 시각(`ko-KR`, 24시간)과 함께 쌓여요.
  - CSS: `.dev-log`(오른쪽 "OS에 넘긴 알림" 목록, `.dev-canvas` 자리), `.dev-side .dev-controls button[data-on]`(고른 버튼, 채팅 대역의 것과 같은 모양). 아이콘은 `Bell`.
  - 시험: `scripts/dev-notify-check.ts`(`npm test`)가 경우가 8개이고 이름이 겹치지 않는지, 보낼 알림이 위 표와 같은지 봐요(프로젝트 이름은 `maestro`로 넣어서. 모두에서는 여덟 경우, 기다릴 때만에서는 승인 기다림·작업 끝·여럿이 한꺼번에, 끔에서는 여덟 경우 모두 없음). 스크립트는 useOsNotify.ts를 불러올 수 없어서 `reason`을 같은 식(`reasonText(rowMeta(…))`)으로 다시 써요.

## 제약과 알려진 문제

- 채팅 창구 시험은 화면에서 확인하지 않았어요(2026-11-18, 타입 검사와 명령 목록 검사만).
- 채팅 창구 시험의 오른쪽은 카드 자리만이에요. 대화 내용과 입력창은 없어요.

- OS 알림 시험은 화면에서 확인하지 않았어요. 진짜 OS 알림이 뜨는지, 알림 센터에 어떻게 보이는지도 확인 안 됨이에요.
- 실행 확인(2026-11-24): 개발 빌드를 WebView2 원격 디버깅으로 띄워 페이지 안에서 버튼을 누르고 결과 글자를 읽어 돌렸어요. 화면을 눈으로 보지는 않았어요. 캔버스 CLI 시험 40개 중 40개, 채팅 창구 시험 8개 중 8개, 깊은 영역 시험 4개 중 4개가 "끝까지 실행"으로 통과했어요(깊은 영역 시험은 아래 결정 기록의 기다림을 늘린 뒤). OS 알림 시험은 열어서 경우 여덟의 보낼 것이 위 표대로 보이고, 시험의 "끔"을 눌러도 설정이 "모두"로 그대로이고, "한 단계"(바로)가 "OS에 넘겼어요 (1개)"가 되는 것까지 봤어요. 그 알림이 화면에 떴는지는 보지 않았어요.
- "바로"는 앱의 포커스 규칙을 건너뛰어요. 포커스 규칙까지 보려면 "5초 뒤"를 고르고 다른 창으로 가요.
- 앱은 OS에 넘긴 것까지만 알아요. 데스크톱에서는 알림 플러그인(tauri-plugin-notification 2.8.1)이 권한을 늘 허용으로 답해서(→ [OS 알림](os-notifications.md) "권한"), OS 쪽에서 앱 알림을 꺼 두어도 "OS에 넘겼어요"가 나와요. "OS가 알림을 막았어요"는 데스크톱에서는 코드로 보면 나오지 않아요. 실제로 떴는지는 화면 구석이나 알림 센터에서 눈으로 봐요.
- 개발 빌드의 알림은 보낸 이가 "Windows PowerShell"로 보여요. 플러그인이 Maestro의 앱 id를 실행 파일이 `target\debug`·`target\release` 밖에 있을 때만 붙여서예요(플러그인 코드 기준). 설치된 앱에서 어떻게 보이는지는 확인 안 됨이에요.

- 화면 확인(2026-11-18): 개발 빌드에서 "dev 모드" → "캔버스 CLI 시험" → "끝까지 실행"으로 그때의 36단계가 모두 통과했고(지금은 40단계: 설명 한 줄, 화면 옮기기, 배치 정리, 너무 긴 설명의 거절이 더해졌고 이것들은 화면에서 확인하지 않았어요), "한 단계", "처음부터", "종료"(시험 캔버스 파일과 `~/.maestro/dev/`가 지워짐)도 동작했어요. 그 뒤 마지막 단계의 `erase --all true`가 질문 블록·질문 묶음·보기 블록도 지우게 바뀌었는데, 이 바뀐 동작은 화면에서 확인하지 않았어요(타입 검사와 시험만). 진짜 CLI를 앱 서버에 붙여 돌리는 시험이라 앱 안에서만 실행할 수 있어요.
- 개발 빌드에서만 입구가 보여요. 설치된 앱에는 "dev 모드"가 없어요(백엔드 명령은 들어 있어요).
